# Data model (T05A)

This document describes the PostgreSQL schema introduced in `prisma/schema.prisma`
and its migrations under `prisma/migrations/`. **It is provisioned ahead of
use**: JSON files (`src/infrastructure/persistence/json/*.repository.js`)
remain the source of truth for `PERSISTENCE_DRIVER=json` (the default in every
environment except production) until T05B implements and cuts over to the
Postgres-backed repositories. No JSON data is read, written or migrated by
this task.

## Why now, without a cutover

- Lets PostgreSQL be provisioned, migrated and exercised (constraints,
  rollback, connection lifecycle) independently of the repository rewrite.
- Fails fast in production: `PERSISTENCE_DRIVER` must be `postgres` and
  `DATABASE_URL` must be set once `NODE_ENV=production` (see
  `src/config/env.js`), even though the repositories behind it land in T05B.
- Avoids a big-bang change: schema review, migration review and repository
  review happen as separate, reviewable steps.

## Entity overview

| Model | Table | Notes |
|---|---|---|
| `User` | `users` | Opaque UUID `id`; `email` unique. |
| `AuthIdentity` | `auth_identities` | External identity per provider. `UNIQUE(provider, subject)`. Google's `sub` is the subject — never the email — because email can change upstream. |
| `AuthSession` | `auth_sessions` | Refresh-token session with rotation family (`family`), hashed token, expiry, revocation. |
| `Balance` | `balances` | Exactly one row per user (`userId` is the primary key and the FK). |
| `LedgerEntry` | `ledger_entries` | Append-only audit trail of every balance movement (`PURCHASE`/`SPEND`/`REFUND`/`ADJUSTMENT`). |
| `Purchase` | `purchases` | Validated store purchase. Stores a hash of the purchase token/receipt, never the raw value. |
| `Package` | `packages` | Sticker pack owned by a user. |
| `Sticker` | `stickers` | Generated sticker, optionally attached to a package. `objectKey` is reserved for the future object-storage cutover. |
| `GenerationJob` | `generation_jobs` | Async AI generation job. `providerPredictionId` is reserved for async provider polling. |

## Identity: Google `sub` vs. email

`AuthIdentity.subject` stores the provider's durable subject identifier
(Google's `sub` claim for `AuthProvider.GOOGLE`), not the user's email.
`@@unique([provider, subject])` is the identity's uniqueness boundary. Emails
live on `User.email` and can change without breaking the link between a user
and their external identity.

## Unique constraints

- `users.email` — one account per email.
- `auth_identities(provider, subject)` — one identity per external subject.
- `auth_sessions.refreshTokenHash`, `auth_sessions.rotatedTo` — a refresh
  token hash (and its single successor in the rotation chain) can only exist
  once.
- `ledger_entries.idempotencyKey` — nullable, but unique when present, so a
  retried balance mutation cannot be double-applied.
- `purchases(provider, purchaseTokenHash)` — the same store receipt cannot be
  redeemed twice for the same provider.
- `balances.userId` (primary key) — enforces exactly one balance row per user.

## Check constraints

Prisma's schema language cannot declare arbitrary `CHECK` constraints, so
they were added by hand in
`prisma/migrations/20260803200000_add_check_constraints/migration.sql`,
reviewed like any other SQL:

- `balances`: `stickerDollars`, `totalPurchased`, `totalSpent`, `version` ≥ 0.
- `ledger_entries`: `amount` > 0 (direction is carried by `type`, magnitude is
  always positive), `balanceAfter` ≥ 0.
- `purchases`: `stickerAmount` > 0.
- `packages`: `stickerCount` ≥ 0.
- `stickers`: `cost` > 0; `width`, `height` > 0 when present; `durationMs`,
  `sizeBytes` ≥ 0 when present.
- `generation_jobs`: `cost` > 0, `attempts` ≥ 0, `progress` between 0 and 100.

Enum-shaped fields (`AuthProvider`, `LedgerEntryType`, `PurchaseProvider`,
`PurchaseStatus`, `PackType`, `ExportStatus`, `StickerStatus`,
`GenerationJobType`, `GenerationJobStatus`) are native PostgreSQL enum types
generated by Prisma, which already reject invalid values at the database
level.

## Delete semantics (`onDelete`)

Deleting a `User` is an explicit, rare operation (e.g. account deletion). The
policy is deliberately not uniform — it depends on whether the child row is
financial/audit data or user content:

| Child | On user delete | Rationale |
|---|---|---|
| `AuthIdentity` | `CASCADE` | Meaningless without the user; pure auth plumbing. |
| `AuthSession` | `CASCADE` | Same as above. |
| `Balance` | `RESTRICT` | Financial state must never disappear silently; deleting a user with an active balance must be handled explicitly (e.g. zero it out first). |
| `LedgerEntry` | `RESTRICT` | Audit trail; must be preserved or archived deliberately, never cascaded away. |
| `Purchase` | `RESTRICT` | Financial/audit record, same reasoning as the ledger. |
| `Package` | `CASCADE` | User-owned content; deleting the account removes its packs. |
| `Sticker` | `CASCADE` (from `User`), `SET NULL` (from `Package`) | Deleting a user removes their stickers; deleting a pack only detaches its stickers instead of destroying generated assets. |
| `GenerationJob` | `CASCADE` (from `User` and `Sticker`), `SET NULL` (from `Package`) | A job is meaningless without its user or target sticker, but should survive its package being removed. |

In short: **cascade user-owned content, restrict money and audit trails.**

## Indexes

Foreign keys used in lookups (`userId`, `packageId`, `stickerId`), status
fields used for polling/filtering (`status`, `exportStatus`), and time-based
queries (`createdAt`, `expiresAt`, `lockedAt`) are all indexed — see
`@@index` entries in `prisma/schema.prisma` and the generated
`CREATE INDEX` statements in the migration.

## Migrations

```
prisma/migrations/
  20260803195826_init/                    # tables, enums, FKs, unique indexes
  20260803200000_add_check_constraints/    # hand-written CHECK constraints
```

Apply against any PostgreSQL 16 instance:

```bash
DATABASE_URL="postgresql://user:pass@host:5432/db" npx prisma migrate deploy
```

`migrate deploy` is idempotent: re-running it against an already-migrated
database reports "No pending migrations to apply" and exits 0. Running it
against an empty database applies both migrations in order.

## Prisma Client

`src/infrastructure/persistence/prisma/client.js` exposes a lazy singleton:

- `getPrismaClient()` creates the client on first use (throws if
  `DATABASE_URL` is not configured).
- `pingDatabase()` runs `SELECT 1`; used by `GET /health/ready` **only when
  `DATABASE_URL` is set**, so the default JSON-driven development setup is
  unaffected.
- `disconnectPrisma()` closes the connection and clears the singleton; called
  from `stopServer()` during graceful shutdown alongside the existing
  background worker teardown.

No repository currently calls into this client — see T05B for the cutover.

## Local development

`compose.dev.yml` provisions a `db` (PostgreSQL 16) service for schema and
migration work. It has **no `ports:` mapping**: it is reachable only from
other containers on the compose network, never from the host or the
internet. `PERSISTENCE_DRIVER` stays `json` by default; opting a local
environment into `postgres` is only for testing ahead of T05B.
